# Skill Graph MCP — Semantic Search + Graph-Based Context Expansion for Claude

> **702 skills. Vector search finds them, graph traversal connects them.**
> Claude automatically loads expert context by querying a Neo4j-backed skill base via MCP.

---

## What is this?

**Skill Graph MCP** is a [Model Context Protocol](https://modelcontextprotocol.io/) server that gives Claude access to a base of 702 expert skills stored in Neo4j. Instead of installing skills manually, Claude autonomously searches, retrieves, and traverses relationships between them to load the right expert context for any task.

```
User: "I want to build a real-time e-commerce site with Stripe"
  └─► Claude calls search_skills("e-commerce stripe payments")
        └─► semantic_score: stripe-integration [0.73], payment-integration [0.75]
              └─► Claude calls get_skill("stripe-integration")
                    └─► Full expert context + related skills loaded → Claude is now a Stripe expert
```

**No `/skill install`. No copy-paste. Claude navigates autonomously.**

### Is this "GraphRAG"?

Not in the strict sense. GraphRAG (as coined by Microsoft Research) means LLM-extracted entity graphs, community detection, and hierarchical summarization for answering questions across an entire corpus. This project doesn't do any of that.

What it actually does is simpler and more honest to describe as **vector search + graph-based context expansion**:
- `search_skills` is plain vector similarity search over embeddings — no graph involved.
- `get_skill` and `navigate` use the graph: fetching a skill also pulls its direct (and optionally 2-hop) neighbors, and Claude can explicitly traverse typed relationships (`REQUIRES`, `ENABLES`, `COLLABORATES_WITH`, ...) beyond whatever similarity search alone would surface.

That combination is a real, useful pattern — it's just not the same architecture the term "GraphRAG" usually points to.

## Key numbers

| Metric | Value |
|---|---|
| Skills in graph | 702 nodes |
| Edges | 4,441 `COLLABORATES_WITH` (2,909 manually curated + 1,532 generated by embedding similarity — see [`registry.cli link`](#registrycli-reference)) |
| Isolated nodes (degree 0) | 2 |
| Embedding model | OpenAI `text-embedding-3-large` (3072 dims) |
| Embedding source | `payload.instructions` (full skill prompt, ~6700 chars avg) |
| Graph database | Neo4j `5.26-community` (Docker) with native vector index |
| Search Precision@5 | 0.875, measured once over 20 hand-picked queries — not a checked-in, re-runnable eval suite (see [Embedding strategy](#embedding-strategy)) |

The relationship schema also defines `REQUIRES`, `ENABLES`, `USES`, `PART_OF`, and `EXTENDS`, but none of the current skill data actually uses them — every edge in the live graph today is `COLLABORATES_WITH`.

## Architecture

Two independent halves that only ever communicate through Neo4j — neither imports the other:

```
┌─────────────────────────────┐        ┌──────────────────────────────┐
│   registry/ (ingestion       │        │   server/ (MCP, read-only)    │
│   engine — offline, writes)  │        │                                │
│                              │        │  search_skills  → vector search│
│  load     : YAML → Neo4j     │        │  get_skill      → node + graph │
│  reindex  : rebuild vector   │        │                   neighbors    │
│             index            │        │  navigate       → edge         │
│  link     : similarity edges │        │                   traversal    │
│             (see below)      │        │  get_knowledge  → safe file    │
└──────────────┬───────────────┘        │                   read         │
               │                        └───────────────┬────────────────┘
               │        both import, neither owns        │
               ▼                                         ▼
        ┌─────────────────────────── core/ ───────────────────────────┐
        │  embeddings.py   : OpenAI client, model/dims constants       │
        │  neo4j_client.py : all Cypher, read and write                │
        └───────────────────────────────┬───────────────────────────────┘
                                         │ bolt://localhost:7687
                              ┌──────────▼──────────┐
                              │   Neo4j (Docker)     │
                              │  702 Skill nodes,    │
                              │  embeddings + edges  │
                              └──────────────────────┘
```

This split exists so the ingestion pipeline (which needs write access and an OpenAI key for embeddings) can run, version, and fail independently of the MCP server Claude actually talks to.

## Quick Start

### 1. Clone and install

```bash
git clone https://github.com/Hassen-Ti/skill-graph-mcp.git
cd skill-graph-mcp
pip install -e .
```

### 2. Configure environment

```bash
cp .env.example .env
# Edit .env and fill in your keys:
#   OPENAI_API_KEY=sk-...
#   NEO4J_PASSWORD=your_password
```

### 3. Start Neo4j

```bash
docker-compose up -d
# Neo4j will be available at http://localhost:7474
# Wait ~30s for startup
```

### 4. Build the knowledge graph

> **Known gap:** this repo does not currently include the enriched skill YAMLs
> (`staging/skills/*.yaml`) or a working SKILL.md → YAML conversion pipeline —
> both were removed from version control. To run this step today you need
> your own directory of skill YAMLs matching `skills/schema.json`. Fixing this
> reproducibility gap is tracked as an open item, not solved by this README.

```bash
# 1 — (Re)create the Neo4j vector index (run once, or after changing dims)
python -m registry.cli reindex

# 2 — Load your skill YAMLs into Neo4j and generate embeddings
python -m registry.cli load path/to/your/skills/ --schema skills/schema.json

# 3 — Optional: auto-generate COLLABORATES_WITH edges from embedding similarity,
#     on top of whatever edges are already curated in your YAMLs
python -m registry.cli link --dry-run   # inspect the count first
python -m registry.cli link             # write them
```

See [`registry.cli` reference](#registrycli-reference) below for all three commands.

### 5. Connect to Claude

Add to your `claude_desktop_config.json` (`%APPDATA%\Claude\` on Windows):

```json
{
  "mcpServers": {
    "skill-graph": {
      "command": "/path/to/python",
      "args": ["-m", "server.main"],
      "cwd": "/path/to/skill-graph-mcp",
      "env": {
        "NEO4J_URI": "bolt://localhost:7687",
        "NEO4J_USER": "neo4j",
        "NEO4J_PASSWORD": "your_password",
        "OPENAI_API_KEY": "sk-..."
      }
    }
  }
}
```

Restart Claude Desktop. The MCP will appear alongside your other servers.

## MCP Tools Reference

### `search_skills(query)`

Semantic search over the skill base using OpenAI embeddings + Neo4j's native vector index. Pure vector similarity — no graph traversal.

| Parameter | Type | Description |
|---|---|---|
| `query` | string | Natural-language description of the capability needed (max 2000 chars) |

**Returns:** Top 3 `SkillCandidate` objects with `semantic_score` and `hub_score`.

```json
[
  {"id": "stripe-integration", "semantic_score": 0.7311, "hub_score": 0.1429},
  {"id": "payment-integration", "semantic_score": 0.7464, "hub_score": 0.1905}
]
```

---

### `get_skill(id, depth="shallow")`

Retrieve the full expert context for a skill, including instructions and its graph neighbors — this is the graph-expansion step.

| Parameter | Type | Description |
|---|---|---|
| `id` | string | Skill node identifier (from search results) |
| `depth` | string | `"shallow"` (1-hop neighbors) or `"full"` (1-hop + 2-hop, 2-hop capped at 20 and filtered to hub_score ≥ 0.6) |

**Rate-limited to 10 calls per session** to control context cost.

---

### `navigate(from_id, edge_type, direction="outbound")`

Explicit graph traversal from a skill node — for exploring relationships beyond whatever similarity search or `get_skill`'s neighbor expansion already returned.

| Parameter | Type | Options |
|---|---|---|
| `from_id` | string | Any skill ID |
| `edge_type` | string | `REQUIRES`, `ENABLES`, `COLLABORATES_WITH`, `USES`, `EXTENDS`, `PART_OF` |
| `direction` | string | `"outbound"`, `"inbound"`, `"both"` |

---

### `get_knowledge(ref)`

Read a knowledge-base document safely (path-confined, extension-whitelisted).

| Parameter | Type | Description |
|---|---|---|
| `ref` | string | Plain filename (e.g. `"api_patterns.md"`) — no path separators |

## `registry.cli` reference

The ingestion engine's CLI (`python -m registry.cli <command>`), separate from the MCP server:

| Command | What it does |
|---|---|
| `load <skills_dir> --schema <path> [--dry-run]` | Validates and loads skill YAMLs into Neo4j: writes nodes, curated edges, `EXTENDS` chains, recomputes `hub_score`, detects cycles, then generates/updates embeddings. `--dry-run` only validates against the schema, no writes. |
| `reindex` | Drops and recreates the Neo4j vector index. Needed once, or after changing embedding dimensions. |
| `link [--top-k N] [--threshold T] [--dry-run]` | Generates `COLLABORATES_WITH` edges between skills whose embeddings are close by cosine similarity, using the same vector index `search_skills` relies on (no GDS/APOC plugin required). Tags generated edges with `source: 'similarity'` on the relationship and never touches a pair already connected by any edge — curated or previously generated. Idempotent: clears its own prior output before recomputing, so it's safe to re-run after re-embedding. Defaults (`top-k=5`, `threshold=0.75`) are a starting point, not a tuned value — always `--dry-run` first when changing them. |

## Graph Schema

```
(:Skill {
  id: String          // unique, lowercase, hyphens allowed
  name: String
  description: String
  type: String        // "domain" | "tool" | "role" | "cluster"
  hub_score: Float    // degree centrality [0.0 - 1.0], recomputed on every load/link
  embedding: Float[]  // 3072-dim vector (text-embedding-3-large, full skill content)
  payload_json: String // JSON: instructions, tools, knowledge
})

[:REQUIRES]          // A cannot function without B            — defined, unused in current data
[:ENABLES]           // A unlocks or enhances B                 — defined, unused in current data
[:COLLABORATES_WITH] // curated in YAML, or auto-generated by `registry.cli link`
                      // (auto-generated ones carry .source = 'similarity' and .score)
[:USES]              // A leverages B as a tool                 — defined, unused in current data
[:EXTENDS]           // A specialises B                         — defined, unused in current data
[:PART_OF]           // A belongs to cluster B                  — defined, unused in current data
```

## Embedding strategy

Five embedding strategies were tested and measured on 20 queries (Precision@5, MRR), as a one-off manual evaluation — there is no checked-in eval script or query set to re-run this measurement after future changes:

| Strategy | Text embedded | P@5 | Notes |
|---|---|---|---|
| V1 — description only | 1–2 sentences | 0.700 | Baseline |
| V2 — rich text | name + desc + caps + reqs | ~0.72 | caps/reqs sparse in dataset |
| V3 — payload.instructions | Full skill prompt (~6700 chars) | **0.875** | **Current** |

Key insight: `payload.instructions` contains explicit technical terms (`MLflow`, `CSRF`, `medallion architecture`) that short descriptions omit — recovering 5 queries where V1 returned 0 precision.

## Security

- API keys via environment variables only
- `get_knowledge`: 3-layer path confinement (`relative_to()`, extension whitelist, symlink resolution)
- Cypher queries use parameterised statements throughout
- Edge type validation via whitelist at MCP tool boundary
- Rate limiting on `get_skill` (10/session)
- One MEDIUM-severity finding (lock file) still open as of the last audit

See [docs/SECURITY_AUDIT.md](docs/SECURITY_AUDIT.md) for the full audit report.

## Skills source

The skill data originates from the [antigravity-awesome-skills](https://github.com/sickn33/antigravity-awesome-skills) repository (732 structured expert prompts). The 702 skills currently in the graph are what's left after removing entries with no usable `SKILL.md`/description and inlining nested sub-skills (e.g. `game-development`'s 10 sub-skills) into their parent rather than keeping them as separate nodes.
