# Authentication & Security Best Practices — Reference

## Password Storage

Never store passwords in plaintext. Never store reversible encrypted passwords.
Use an adaptive hashing algorithm designed for passwords — not a generic hash like SHA-256.

**bcrypt** is the standard choice for most applications:
- Cost factor of 12 is the minimum recommended as of 2024 (adjust up as hardware improves).
- bcrypt automatically salts each password — do not add a manual salt before passing to bcrypt.
- bcrypt truncates at 72 bytes; for passwords longer than 72 bytes, pre-hash with SHA-256 and base64-encode before passing to bcrypt. Document this in your security model.

```python
import bcrypt

# Hash a password
hashed = bcrypt.hashpw(password.encode(), bcrypt.gensalt(rounds=12))

# Verify
bcrypt.checkpw(password.encode(), hashed)
```

Argon2id is the current OWASP recommended choice for new systems (winner of the Password Hashing Competition):
- Memory-hard — resists GPU and ASIC attacks better than bcrypt.
- Parameters: m=64MB, t=3 iterations, p=4 parallelism as a starting point.

Never use MD5, SHA-1, or unsalted SHA-256 for password storage. These are broken or inadequate for this use case.

## JWT — JSON Web Tokens

JWT is a signed token format used for stateless authentication. Understand what it provides and what it does not.

**Structure:** `header.payload.signature` — all base64url-encoded.

**Signing algorithms:**
- Use **RS256** (RSA + SHA-256) or **ES256** (ECDSA + SHA-256) for production systems. Asymmetric — verification keys can be distributed without exposing the signing key.
- **HS256** (HMAC + SHA-256) is acceptable for single-service internal tokens where both issuer and verifier are the same system. Never use HS256 across service boundaries.
- **Never use `alg: none`** — this disables signature verification entirely. Reject any JWT presenting `alg: none`.

**Validation checklist — verify ALL of these on every request:**
1. Signature is valid (use the correct algorithm and key)
2. `exp` (expiry) has not passed
3. `nbf` (not before) is in the past, if present
4. `iss` (issuer) matches the expected issuer
5. `aud` (audience) includes your service identifier
6. `sub` (subject) maps to an existing, non-deleted user

Never accept a JWT that fails any of these checks. Log the failure reason (for diagnostics), but return a generic 401 to the client.

**Token expiry:**
- Access tokens: short-lived (5–15 minutes for high-security, 1 hour for standard web apps).
- Refresh tokens: longer-lived (7–30 days), stored server-side with revocation capability.
- Never issue non-expiring JWTs.

**Storage in browser clients:**
- HttpOnly, Secure, SameSite=Strict cookie: safest option — not accessible to JavaScript, protects against XSS.
- Memory (JavaScript variable): cleared on page close, vulnerable to XSS if any script runs in the same context.
- localStorage / sessionStorage: accessible to any JavaScript on the page. Do not use for auth tokens unless you have a very strong reason and a comprehensive XSS defense strategy.

## OAuth 2.0 and OpenID Connect

**OAuth 2.0** is an authorization delegation framework, not an authentication protocol.
**OpenID Connect (OIDC)** is a thin identity layer on top of OAuth 2.0 that adds authentication.

Use OAuth 2.0 / OIDC for:
- Third-party login (social login, enterprise SSO)
- Delegating access to APIs on behalf of a user

**Authorization Code Flow with PKCE** is the correct flow for all public clients (browser apps, mobile apps) in 2024:
1. Client generates a `code_verifier` (random 43–128 char string) and `code_challenge` (SHA-256 of verifier, base64url-encoded).
2. Authorization request includes `code_challenge` and `code_challenge_method=S256`.
3. Authorization server returns an `authorization_code`.
4. Token request includes the original `code_verifier`. Server verifies the challenge.

This prevents authorization code interception attacks.

**Implicit Flow is deprecated** — do not use it for new applications. All major identity providers have removed it or discourage it.

**Scopes:** Request only the scopes your application needs. The principle of least privilege applies to OAuth scopes. Never request `*` or admin scopes unless your application genuinely requires them.

**State parameter:** Always include a cryptographically random `state` parameter in the authorization request and validate it in the callback. This prevents CSRF attacks against the OAuth flow.

## Session Security

**Session ID requirements:**
- At least 128 bits of entropy generated by a CSPRNG.
- Regenerate the session ID after any privilege escalation (login, MFA completion, password change).
- Invalidate the old session ID immediately after regeneration.

**Cookie settings for session cookies:**
```
Set-Cookie: session=...; HttpOnly; Secure; SameSite=Strict; Path=/; Max-Age=3600
```
- `HttpOnly` — prevents JavaScript access.
- `Secure` — HTTPS only.
- `SameSite=Strict` — blocks the cookie from being sent in cross-site requests.

**Session termination:** On logout, invalidate the session server-side. Do not rely solely on clearing the cookie — if the token was intercepted, clearing the client-side cookie does not revoke it.

**Absolute timeout:** Even active sessions must expire. 8–24 hours is typical for web applications.
**Idle timeout:** Terminate sessions after a period of inactivity (15–60 minutes depending on sensitivity).

## Common Vulnerabilities

**Broken Object Level Authorization (BOLA / IDOR):**
Never assume a user has access to a resource just because they know its ID. Always verify ownership or permission on every request. Example: `GET /orders/{id}` must check that the authenticated user owns order `id`.

**Mass Assignment:**
Never pass raw request bodies directly to ORM save operations. Whitelist allowed fields explicitly. A user setting `{"is_admin": true}` in a profile update request should not be able to escalate privileges.

**Timing Attacks:**
Use constant-time comparison for secrets (tokens, signatures, passwords). In Python, use `hmac.compare_digest()` instead of `==` for comparing secrets.
```python
import hmac
hmac.compare_digest(known_token, provided_token)  # safe
known_token == provided_token                      # vulnerable to timing attack
```

**Token Logging:**
Never log full tokens, passwords, or session IDs. Truncate or hash before logging. Scan your log pipelines for accidental token leakage.
